Why · 为什么会有这个项目

测试工程师每天绕不开的三个痛点

Test Generator 把「AI 生成测试用例」从 demo 拉到工程级——结构化、可追溯、可评审。

PAIN 01

用例产出慢

4 小时/功能，手写用例的速度永远追不上迭代节奏。

→ 15 分钟内产出一版能用的用例
PAIN 02

AI 生成用例不敢用

幻觉严重、覆盖率不可控，生成的用例没法直接进评审。

→ 结构化、可追溯、可评审的产物
PAIN 03

多工具协作成本高

Claude / Codex / Qoder / Cursor 各玩各的，方法论无法复用。

→ 一套 Skill，{{HOST_COUNT}} 个宿主通用

生产级架构

  • 六阶段流水线：输入预处理 → 需求预处理 → 代码分析 → 领域建模 → MBT 设计 → 用例生成
  • 质量门禁系统：关键阶段完成后可进行质量检查与一致性校验
  • 双向可追溯：需求 ↔ 测试用例之间可建立追溯矩阵
  • 反馈闭环：根据执行结果、漏测场景和规则修正持续优化产物

智能 AI 能力

  • 多格式输入：需求文档、PRD、API 规范、源代码、自然语言描述
  • 输入质量预处理：规范化、质量评分与缺口识别先行
  • 歧义与风险识别：发现模糊需求、边界遗漏、潜在冲突与测试盲区
  • 本地知识库检索：术语表 / 项目规范 / 历史用例的触发式 BM25 检索，用例追溯保留 KB: 引用
  • 增量代码扫描：从 unified diff 提取新增行，识别硬编码密钥、裸 except、SQL 拼接等风险信号

专业测试工程

  • MBT 方法论：围绕领域模型、状态迁移、覆盖准则组织测试设计（对齐 ISO/IEC/IEEE 29119-3:2021）
  • 边界值 + 等价类：系统化支持 BVA / EP / 决策表等分析方法
  • 状态机推导：自动构建状态转换规格与路径集合
  • 参数空间优化：Pairwise、组合裁剪与风险导向覆盖

多场景覆盖

  • 正向 / 负向：Happy Path 与异常场景结合
  • 接口 / 领域 / 状态：API、业务流程、状态型系统测试
  • 回归 / 审计 / 标准化：测试补齐、测试审计、统一格式化输出
  • 自动化适配：为 Pytest / Playwright / Cucumber 落地提供基础骨架

Pipeline · 六阶段智能流水线

每一阶段都有独立提示词 + 质量门禁

门禁阈值随阶段递增（80 → 90）。信息不足时不强行出全量用例，而是走降级路径输出测试点清单与风险摘要。点击任意阶段查看详情。

↓↓↓↓↓↓
六个阶段不是强串行链：只有 PRD → P0 → P1 → P5；只有 API 规范 → P0 → P2 → P5； 状态机 / 复杂规则 → 叠加 P3 → P4。编排者必须先做输入识别再决定路径—— 详见 多 Agent 划分参考。

Architecture · 分层架构

一份 manifest 贯穿全层的契约式设计

skill.manifest.json 是版本唯一数据源 + 分发边界定义，被激活器、打包脚本与三层审计共同读取； 凡可由源生成的内容一律不手写。

Agent Prompts · 多 Agent 划分参考

P5 的 90 分对应 skill_quality_audit 的 FORMAL_SCORE_THRESHOLD——只有达到它，产物才可声明为「正式测试用例」，低于阈值只能交付草稿。

三层一致性审计 · 50+ 项机器检查

  • 声明层 · capability_audit（30 项）：能力矩阵、必需路径、版本对齐、Schema 有效性
  • 内容层 · skill_quality_audit（6 项）：frontmatter 标准字段、用例必备字段、流水线完整性
  • 结构层 · doc_consistency_audit（20 起）：跨文件一致性、宿主三方一致、npm 发布载荷守卫
  • CI 矩阵：Node 18 / 20 / 22 三档，让 engines: >=18 的声明真正被验证
